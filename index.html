Scenario — the oCFO Agent Platform

A worked, end-to-end scenario for office of the CFO: one governed entry point that answers finance, workforce, spend and supplier questions across systems.

The story

oCFO wants leaders to ask questions in plain language — "what's our FY26 take rate?", "attrition by department?", "how much travel spend is out of policy?", "which suppliers are due for renewal?", "what did the annual report say about capital allocation?" — and get governed, trustworthy answers without knowing which system or dataset holds the truth. We build that as a Multi-Agent Supervisor over specialised Genie agents, a document Knowledge Assistant, and governed calculation tools, all on the Databricks Data Intelligence Platform.

Source systems & domains

  • Office of the CFO — group P&L, TTV, revenue, margin, working capital (DSO/DPO/DIO/CCC), FX, regional performance
  • Workday — headcount, hiring, attrition, tenure, compensation
  • SAP Concur — employee travel & expense spend, out-of-policy, merchants
  • SAP Ariba — supplier spend, savings, risk, contract renewals
  • Financial-results documents — annual & half-year results, trading updates, capital & liquidity (PDFs)

What we build

  • Certified metric views on each domain's KPIs (one governed definition)
  • 4 curated Genie agents (oCFO, HR, Travel, Supplier) with benchmark questions
  • Knowledge Assistant over the results PDFs — the documents subagent
  • UC function tools (FX convert, cash-conversion-cycle, fiscal period, % change)
  • Supervisor Agent routing across all of the above, governed by Unity Catalog & Unity AI Gateway
  • Shipped dev→preprod→prod via a Declarative Automation Bundle, with MLflow tracing & evaluation

How a question flows

  • A user asks the Supervisor a natural-language question
  • The Supervisor routes to the right subagent from its description (Genie space, Knowledge Assistant, or tool)
  • Genie agents query certified metric views; the KA retrieves from the results PDFs; tools compute derived values
  • The answer is composed and returned, noting which domains contributed — every step traced in MLflow

Why it matters

  • One governed front door instead of four disconnected systems
  • Consistent KPIs — metric views mean everyone gets the same number
  • Least-privilege access; users only reach data they're permitted to
  • Quality is measurable (benchmarks + judges) and promotable (CI/CD)

Reference architecture

End-to-end: source systems (Workday, Concur, Ariba, Finance) → Lakeflow ingestion → medallion + Lakehouse/Lakebase → certified metric views & Genie Ontology → Genie agents, Knowledge Assistant and Supervisor, all governed by Unity Catalog & Unity AI Gateway.

Genie — Best Practices

Build, curate and tune high-quality Genie agents grounded in governed data.

Genie space delivery

  • Use curated tables, clear metric definitions, and strong examples
  • Store prompts, instructions, and benchmark questions in Git
  • Run benchmark regressions before promoting environment changes
  • Use dev, test, and production promotion gates for safer rollout

Executive talking points

  • Governed self-service reduces time to insight
  • Benchmarking and CI/CD reduce trust erosion from regressions
  • Supervisor patterns unify data, documents, and actions behind one entry point
  • Observability makes AI experiences measurable and improvable

Genie Ontology

The ontology layer gives Genie the business context it needs to write accurate SQL without guessing.

Knowledge Snippets Curated definitions, metric formulas, and domain rules stored alongside your data
Semantic Definitions Column descriptions, join keys, and filter conventions that guide query generation
Business Glossary Standardized terms (e.g. "active customer", "churn") so Genie and analysts share one language
Governed Tags & Comments Unity Catalog tags and column comments that propagate context to every downstream consumer

Best practices that make Genie trustworthy

  • Prefer structured context (descriptions, synonyms, joins, example SQL) over long free-text prompts
  • Keep each space small and domain-focused — aim for 5 or fewer sources
  • Describe tables and columns in business language; hide noisy technical fields
  • Define joins explicitly — don't let Genie guess relationships
  • Build a benchmark of ≥10 (ideally ≥30) representative questions and measure accuracy
  • Set a strong agent description — it doubles as the Supervisor's routing signal

More ways to improve a Genie space — from the tuning guide

The official Genie tuning guide recommends these — most are structured surfaces, not prose.

SQL expressions & examples

  • Example SQL for common questions, with usage guidance on when each applies
  • Parameterize verified example queries so values can vary
  • Filter expressions for reusable business conditions (e.g. "high-value orders")
  • Measure expressions for KPIs and field expressions for grouping/derived attributes
  • Register SQL functions in Unity Catalog for complex reusable logic

Metadata & value matching

  • Column synonyms mapping business terms to column names
  • Format assistance — representative values so Genie learns each column's shape
  • Entity matching — store distinct categorical values (up to 120 columns) for accurate filters
  • Hide confusing or duplicate columns from Genie's context

Guiding the conversation

  • Phrase example-question titles to match real user language
  • Prompt Genie to ask a clarifying question when a request is ambiguous
  • Customize summaries — rounding rules, mandatory caveats, state the date range used
  • Choose the right instruction type — encode rules in structured surfaces before general instructions

Keep it healthy

  • Review for inconsistencies — resolve conflicting or ambiguous guidance
  • Knowledge mining — accept Genie's suggested new SQL expressions & joins
  • Re-run your benchmark after every change to catch regressions

7 · SQL guidance≥1 of: SQL functions, expressions, measures, filters, example SQL
8 · Entity / format matching≥1 column with value/format assistance for accurate filters
9 · Benchmark questions≥10 benchmark questions for measurable accuracy

Supervisor Agent

Orchestrate multiple Genie agents, Knowledge Assistants and tools behind one entry point — with reliable routing, governance and evaluation.

When to use a Supervisor

  • A question spans multiple domains, agents, or tools
  • Users shouldn't need to know which agent to ask
  • You want one governed entry point over many Genie spaces, Knowledge Assistants and tools

Supervisor patterns

  • Use Supervisor Agent for multi-domain questions across tools or subagents
  • Write precise tool and subagent descriptions for better routing
  • Apply least-privilege access so users only reach permitted sources
  • Keep examples current and representative of executive workflows

Directing the Supervisor — routing that doesn't get lost

A Supervisor routes each question to one child agent based on its description. Misrouting is almost always a description / instruction problem — not a model problem.

Master prompt (supervisor instructions)

  • State the supervisor's role and explicit routing rules ("bookings & revenue → Travel Analytics Genie; policy → Knowledge Assistant")
  • Tell it to ask a clarifying question when a request is ambiguous or spans domains
  • Define a fallback for out-of-scope questions so it degrades gracefully
  • Keep it to global behavior — domain facts belong in the child agents, not here

Tool & agent descriptions

  • Make each description specific and non-overlapping — "Corporate-travel bookings: volume, revenue, TMC performance by region", not "travel data"
  • Distinct boundaries stop two agents from both looking like the right target
  • Every Genie space needs its own strong description (IQ check #1)
  • The description is the routing signal — invest in it

Examples, tools & skills

  • Add example questions paired with the expected agent — the highest-leverage fix for stubborn misrouting
  • Reuse governed Unity Catalog functions and AI skills as tools for actions, not just Q&A
  • Attach external systems via MCP connections for write / operational tasks
  • Test with real phrasings and sharpen descriptions where routing misses

Scale with hierarchy

  • Group related Genie spaces under domain sub-supervisors, then a top supervisor over those
  • Smaller routing decisions at each level = less "lost context"
  • Apply least-privilege so users only reach permitted sources
  • A supervisor can't rescue a weak Genie space — get each to "Trusted" first

Example routing rules — drop into the supervisor's instructions

A concrete, reusable routing policy. Adapt the agent names to your own Genie spaces, Knowledge Assistants, and tools.

  1. Use the Revenue Genie for structured revenue, bookings, ARR, churn, customer, product, and region questions.
  2. Use the Policy Assistant for policies, contracts, procedures, and documents.
  3. Use Operations Tools only when the user explicitly requests an action.
  4. Call multiple agents only when the question genuinely spans domains.
  5. Do not call an agent merely to confirm information already established.
  6. If the question is ambiguous, ask one concise clarification question.
  7. Never invent a result when a sub-agent returns no answer.
  8. In the final response, identify which domains contributed to the answer.

Reusable, governed tools & AI skills — Unity Gateway

Register once, reuse everywhere. Unity Gateway extends Unity Catalog governance to runtime AI — models, MCP servers, tools/functions, and agents become governed, shareable building blocks a Supervisor can call.

AI assets as Unity Catalog securables

  • Register models, MCP servers, UC functions/tools, and agents as governed objects
  • Control access with standard Unity Catalog grants — least privilege by default
  • Rate limits, guardrails, usage tracking, cost attribution, and audit logging
  • Share a tool once — any authorized agent can reuse it
Unity Gateway docs →

How it strengthens the Supervisor

  • Add governed tools to the Supervisor as UC functions, MCP connections, Genie spaces, or agent endpoints
  • The Supervisor inherits the caller's permissions — it can only invoke what the user may access
  • Reusable skills mean less duplication and consistent governance across every agent
  • Every tool call is auditable end to end
Unity Gateway overview →

Add skills & tools to a Supervisor

Give the supervisor new capabilities by attaching governed building blocks — each becomes a routable agent or tool.

What you can attach

  • Genie spaces — natural-language SQL over a data domain
  • Knowledge Assistants — document Q&A (RAG)
  • Unity Catalog functions — governed SQL/Python tools for actions
  • MCP servers (via UC connections) — external systems & operations
  • Model-serving endpoints — custom or fine-tuned agents

How to add one

  • Register/govern the tool in Unity Catalog and grant the agent's service principal access (least privilege)
  • Add it to the supervisor with a specific, non-overlapping description — that's the routing signal
  • Add 1–2 example questions that should route to it
  • Re-test routing — the supervisor inherits the caller's permissions

Trace, evaluate & monitor your Supervisor — MLflow 3

See why the supervisor routed the way it did, and catch quality regressions before users do.

Tracing & evaluation

  • MLflow Tracing captures each turn — routing decision, sub-agent calls, tool I/O, latency & tokens
  • Scorers & LLM judges (built-in + custom) score correctness, completeness, and routing quality
  • Build evaluation datasets from real traces to compare versions and detect regressions
  • The Review App collects domain-expert feedback to align judges

Production monitoring

  • Run scorers automatically on production traces to monitor quality continuously (Beta)
  • Store traces in Unity Catalog for governance and querying
  • Encode routing-accuracy and "spans multiple agents" as custom scorers

CI/CD — ship the whole agent stack as code

One consolidated Declarative Automation Bundle (DABs) that promotes the entire oCFO agent platform across dev → preprod → prod workspaces.

What the bundle ships

  • Data layer — governed UC function tools + certified metric views (catalog-parameterized, idempotent)
  • Genie layer — 4 curated Genie spaces as native genie_spaces DABs resources, each backed by a versioned .geniespace.json
  • Supervisor — managed Multi-Agent Supervisor over the Genie spaces + Knowledge Assistant + UC tools, created & attached via the Agent Bricks REST API in the deploy job (Terraform alternative for the shell)
  • All tools and instructions live in the bundle — edit, commit, redeploy
View the DABs project on GitHub →
Read the CI/CD notes →

Promotion model (dev → preprod → prod)

  • Everything is catalog-parameterized; each environment sets its own catalog
  • The .geniespace.json files are the source of truth — every workspace converges on redeploy
  • mode: development vs mode: production targets with per-env variables
  • Genie spaces deploy declaratively (bundle deploy); a job builds the data layer and creates + attaches the supervisor via REST

How the bundle works

Under the direct engine, Genie spaces are a first-class DABs resource: bundle deploy creates them from their versioned JSON. A DABs job then builds the data layer and creates the supervisor + attaches its sub-agents/tools via the Agent Bricks REST API (POST /api/2.1/supervisor-agents and .../{id}/tools), reading each Genie space's id via ${resources.genie_spaces.<key>.id}. Requires Databricks CLI ≥ 1.16.x.

ocfo-agent-platform/ 
databricks.yml                       # bundle (engine: direct) · vars · genie_spaces · dev/preprod/prod
config/supervisor_instructions.yml   # master prompt · routing rules · agent descriptions
genie/*.geniespace.json              # versioned definition per Genie space (file_path)
src/deploy_data_layer.py             # UC functions + metric views (idempotent)
src/create_supervisor.py             # create + attach supervisor via /api/2.1 REST
resources/ocfo_platform.job.yml      # job: data layer → create+attach supervisor (REST)
terraform/                           # databricks_supervisor_agent (supervisor lifecycle as code)

Genie space — native DABs resource

databricks.yml 
bundle:
  name: ocfo_agent_platform
  engine: direct           # required for the genie_spaces resource

resources:
  genie_spaces:

Supervisor lifecycle — REST (primary) & Terraform (alternative)

The deploy job creates the supervisor and attaches its sub-agents/tools via the Agent Bricks REST API (/api/2.1/supervisor-agents) — this is how the Genie spaces, Knowledge Assistant and UC-function tools are wired in. For teams that prefer a declarative shell, the terraform/ module manages the supervisor + instructions with databricks_supervisor_agent and exports the serving endpoint + MLflow experiment id for the Phase-7 eval gate — but the Terraform resource can't attach sub-agents yet, so the REST path does the attachment.

create_supervisor.py — Agent Bricks REST API 
from databricks.sdk import WorkspaceClient
w = WorkspaceClient()

# 1) create the supervisor (fields at top level)
sup = w.api_client.do("POST", "/api/2.1/supervisor-agents", body={
    "display_name": "oCFO Enterprise Supervisor",
    "instructions": instructions,   # versioned routing policy
})
sid = sup["supervisor_agent_id"]

# 2) attach each sub-agent / tool
for tool_id, tool in tools:            # genie_space | knowledge_assistant | uc_function
    w.api_client.do("POST", f"/api/2.1/supervisor-agents/{sid}/tools",
                    query={"tool_id": tool_id}, body=tool)

# tool examples:
# {"tool_type":"genie_space",         "genie_space":{"id": genie_id}}
# {"tool_type":"knowledge_assistant", "knowledge_assistant":{"knowledge_assistant_id": ka_id}}
# {"tool_type":"uc_function",         "uc_function":{"name":"catalog.agent_tools.fx_convert"}}

Idempotent — reuses the supervisor by display_name and only attaches missing tools. Alternative (declarative shell):

terraform/main.tf 
resource "databricks_supervisor_agent" "ocfo" {
  display_name = "oCFO Enterprise Supervisor"
  description  = "Routes across oCFO, HR, Travel & Supplier Genie agents + KA + UC tools."
  instructions = local.instructions   # versioned routing policy
}
# exports: endpoint_name, experiment_id, supervisor_agent_id  → feed the eval notebook

The pipeline is DABs → eval gate: bundle deploy creates the Genie spaces, then bundle run builds the data layer and creates + attaches the supervisor via REST. The Terraform module is an alternative for managing the supervisor shell declaratively; sub-agent attachment stays on the REST path (.../{id}/tools) until the provider adds subagent blocks.

Deploy & promote

promote.sh 
# 1) data layer + Genie spaces + tools (DABs)
databricks bundle validate --target dev
databricks bundle deploy   --target dev
databricks bundle run ocfo_agent_platform_deploy --target dev

# 2) bundle run (above) already created + attached the supervisor via REST
#    optional — manage the supervisor shell declaratively instead:
# cd terraform && terraform init && terraform apply

# 3) quality gate: MLflow eval against the supervisor serving endpoint (mas-*-endpoint)

# promote the same code to preprod, then prod (repeat 1-3 per target)
databricks bundle deploy --target prod && databricks bundle run ocfo_agent_platform_deploy --target prod

No credentials live in the bundle — auth comes from your CLI profile, and the deploy path is scoped per-user via ${workspace.current_user.userName}.

Agent Memory

Give your agents persistence — short-term session state and long-term semantic recall, powered by Lakebase.

Managed Memory

Databricks handles storage, indexing, and lifecycle automatically. Ideal for production agents where you want zero infrastructure overhead.

  • Built-in checkpoint store for resumable conversation threads
  • Semantic memory with pgvector-backed embeddings via Databricks endpoints
  • Automatic TTL, compaction, and garbage collection
  • No infrastructure to provision — just configure project, branch, and schema
Managed Memory Docs →

Self-Managed Memory

Bring your own storage backend when you need full control over the persistence layer, custom retention policies, or hybrid architectures.

  • Plug in any checkpoint or store backend (Redis, Postgres, custom)
  • Full control over schema, indexing, and eviction strategies
  • Suitable for multi-cloud or air-gapped deployments
  • Use alongside managed memory for hybrid patterns
Self-Managed Memory Docs →

Initializing Agent Memory with LangGraph

The databricks_langchain package provides async-ready checkpoint and store classes that wire directly into LangGraph’s persistence layer.

agent_memory.py 
from databricks_langchain import AsyncCheckpointSaver, AsyncDatabricksStore

# Short-term: thread/session checkpoints — resumable runs.
async with AsyncCheckpointSaver(
    project=PROJECT,
    branch=BRANCH,
    schema=SCHEMA,
) as checkpointer,
AsyncDatabricksStore(
    # Long-term + semantic: pgvector-backed memory,
    # embedded via a Databricks endpoint.
    project=PROJECT,
    branch=BRANCH,
    schema=SCHEMA,
    embedding_endpoint="databricks-gte-large-en",
    embedding_dims=1024,
) as store:
    yield checkpointer, store

Key Concepts

  • AsyncCheckpointSaver — persists LangGraph thread state so conversations survive restarts
  • AsyncDatabricksStore — semantic key-value store backed by pgvector for long-term recall
  • Embedding endpoint — uses Databricks model serving (e.g. databricks-gte-large-en) for vector similarity
  • Project / Branch / Schema — Lakebase coordinates that isolate memory per environment

When to Use Each

  • Checkpoints only — stateful multi-turn chat, tool-calling agents with resumable sessions
  • Store only — user preferences, learned facts, cross-session context
  • Both together — production agents that remember the current thread and recall past interactions
